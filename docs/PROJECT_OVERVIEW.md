# Preduit / Forecaster — Project Overview

A B2B wholesale demand forecasting system that uses SARIMA and CatBoost models to predict future orders, then serves results via a FastAPI backend to a Next.js dashboard.

## Package Roles

### `preduit-engine` — The ML Pipeline Library

Contains all forecasting logic. Has no knowledge of deployment, API, or client-specific paths.

| Module | Purpose |
|--------|---------|
| `m1_data_preparation` | Loads raw CSV, standardizes columns, computes `true_demand`, aggregates monthly series |
| `m2_model_assignment` | Analyzes history depth per SKU, assigns SARIMA or CatBoost model type |
| `m3_kpis` | Computes business KPIs: diffusion rate, reorder rate, fill rate, depth per client |
| `m4_sarima` | Fits SARIMA models for SKUs with long history (36+ months) |
| `m5_catboost` | Gradient boosting forecasts for shorter-history SKUs, produces quantile forecasts |
| `m6_size_curves` | Distributes color-level forecasts to individual sizes using historical curves |
| `m7_recommendations` | Combines forecasts with stock/orders to compute net-to-order quantities |
| `m8_output` | Exports results to CSV and Excel files |
| `database` | SQLite schema creation, index management, `populate_database()` |
| `ingestion` | Incremental data ingestion: append CSVs, normalize, deduplicate, upsert |
| `config` | Algorithm parameters (horizon, SARIMA order bounds, CatBoost hyperparams, size ordering) |

### `preduit-app` — The Client Service

Deployment-specific layer. Depends on `preduit-engine`.

| Module | Purpose |
|--------|---------|
| `client_config` | Paths (data file, DB, output), API host/port, CORS, ERP column names, business policy |
| `main` | CLI entry point — runs the full pipeline (m1→m8 + DB populate) |
| `api_server` | FastAPI app serving the frontend: articles, filters, customers, ingest, budget, SSE |
| `check_setup` | Validates environment, files, and dependencies |
| `test_db` | Smoke tests for DB contents and API query logic |

### `frontend` — Next.js Dashboard

A React app (Next.js 14 with app router) that displays forecasts, stock matrices, recommendations, and customer analytics.

Key pages: Dashboard, Products, Recommendations, Customers, Budget, Projection, Validation, Setup.

Tech: Tailwind CSS, Radix UI, Zustand state management, Recharts for charts.

## Complete Software Offering and User Flow

This section explains the product from a user and presentation perspective. It describes what the complete software offers to business users, then walks through the full operational flow from initial setup to daily decision-making and export.

### What the Software Offers to Users

Preduit / Forecaster is a complete B2B wholesale forecasting and buying decision platform. It takes historical ERP sales/order data, runs an ML forecasting pipeline, enriches the results with inventory and supplier-order information, then presents the output in a web dashboard where users can understand demand, review product-level recommendations, validate forecast quality, and decide what to buy or replenish.

At a high level, the software helps users answer these business questions:

- What demand should we expect for each product, color, and size?
- Which products require additional purchasing from suppliers?
- Which products already have enough stock or supplier pipeline coverage?
- Which SKUs are high-risk because the forecast confidence is low?
- Which products are overstocked, understocked, or aligned with budget?
- Which customers are covered, which customers are not visited, and which visited customers can be used as comparison profiles?
- How does the forecast compare with the season budget and target margin?
- Which recommendations should be accepted, reviewed, locked, exported, or refreshed?

#### 1. Forecasting and Demand Prediction

The core offering is automated demand forecasting for wholesale products. The system reads historical ERP order data from CSV files and uses the forecasting engine to predict future demand.

The engine uses two model families:

- **SARIMA** for SKU/color histories with long enough time series.
- **CatBoost** for products with shorter or more complex demand histories.

The forecast is produced at product, color, and size level. This is important for fashion/wholesale businesses because a total article forecast is not enough: buyers need to know how demand splits across sizes and colors before placing supplier orders.

The software produces multiple demand scenarios:

- **Conservative forecast**: lower demand estimate.
- **Base forecast**: primary recommended demand scenario.
- **Optimistic forecast**: higher demand estimate.

These scenarios help users make buying decisions with risk awareness instead of relying on a single number.

#### 2. Product and SKU-Level Visibility

The Products page gives users a searchable view of the product catalog with business context. It includes product identifiers, supplier, family, theme, model, style/designation, season, forecast values, stock indicators, and supporting metadata.

Users can use this view to:

- Browse the product assortment.
- Search for a specific reference, model, family, supplier, or theme.
- Understand which articles are included in the forecast.
- Review style/designation information from the ERP data.
- Move from high-level catalog visibility into detailed forecast and recommendation workflows.

#### 3. Stock Matrix and Size-Level Forecasting

One of the most important outputs is the stock matrix on the Projection page. It shows product demand and supply position across sizes.

For each selected SKU/color, users can inspect:

- Forecasted quantity by size.
- Current stock by size.
- Supplier order / pipeline quantity by size.
- Total supplier quantity.
- Net requirement logic that compares demand with available supply.

This helps users avoid two common buying mistakes:

- Buying too much of sizes that already have stock coverage.
- Missing demand in specific sizes even when the total product-level stock looks acceptable.

The matrix also supports dynamic size columns, so it can handle different size systems such as XS/S/M/L, numeric sizes, or product-specific size scales.

#### 4. Recommendations for Buying Decisions

The Recommendations page turns raw forecast outputs into actionable buying recommendations. Instead of only showing demand, it highlights what the business should do next.

Users can review recommendations such as:

- Products that need additional supplier orders.
- Products with high expected demand.
- Products where stock plus supplier pipeline does not cover forecasted demand.
- Products with high or low forecast confidence.
- Items that may require manual review before buying.

The system includes confidence and risk indicators so the buying team can separate straightforward purchasing decisions from products that need closer review.

Users can also lock or unlock recommendations. This supports a human-in-the-loop workflow where a buyer can preserve a decision and prevent it from being overwritten by later recalculations.

#### 5. Budget and Financial Control

The Budget page connects forecasted demand to financial planning. It compares projected buying requirements against the configured season budget and margin target.

The software supports:

- Season budget configuration.
- Target margin configuration.
- Forecast spend visibility.
- Expected revenue and margin calculations.
- Budget utilization review.
- Identification of whether proposed buying decisions are financially aligned.

This helps users move from operational forecasting to commercial planning. The product is not only answering "how many units do we need?" but also "does this buying plan fit the financial target?"

#### 6. Dashboard for Executive Overview

The Dashboard page gives users a summary of the current forecast state and operational health.

It provides high-level indicators such as:

- Total forecast quantity.
- Expected turnover.
- Gross margin.
- Purchase cost estimate.
- Client coverage.
- Risk items.
- Forecast confidence distribution.
- Recent refresh or pipeline status.

This page is useful for managers and decision-makers who need a quick understanding of whether the season is on track before going into detailed pages.

#### 7. Customer Coverage and Customer Analytics

The Customers page helps users understand customer coverage using real customer and order data from the `clients` and `client_orders` tables.

It offers:

- Real customer list from ERP-derived data.
- Visited / not visited status based on latest-season order behavior.
- Region/geography grouping.
- Derived customer typology such as independent, chain, or key account.
- Average basket estimate.
- Product categories bought by each customer.
- Purchase history by SKU and season.
- Similarity matching between not-visited and visited customers.

This gives sales and merchandising teams a customer-focused view of the forecast. For example, if a customer has not yet ordered in the current/latest season, the system can match them to similar visited customers based on region, typology, basket profile, and product categories. This helps guide follow-up actions and demand assumptions.

#### 8. Forecast Validation and Quality Review

The Validation page is designed for checking the quality and reliability of the forecast.

It helps users review:

- Forecast confidence.
- Risk distribution.
- Forecast vs historical behavior.
- Product-level validation indicators.
- Items that may require manual review before final buying decisions.

This is important because the system is not only generating predictions; it also exposes signals that help users decide how much trust to place in each recommendation.

#### 9. Setup, Season Configuration, and ERP Sync

The Setup page guides users through the operational configuration needed before using the forecasting workflow.

It supports:

- Creating or updating season configuration.
- Setting the season budget.
- Setting the target margin.
- Triggering ERP data sync/ingestion.
- Starting a forecast refresh.

This allows the system to be reused season after season. Users can configure a new season, load the latest ERP data, refresh the forecast, and then review the updated recommendations in the dashboard.

#### 10. Data Ingestion and Refresh Workflow

The system supports ERP-driven data refresh through ingestion endpoints. Data can come from a raw CSV export or from a simulated ERP sync flow.

The ingestion and refresh flow supports:

- Loading new order data.
- Deduplicating appended records.
- Updating SQLite serving tables.
- Refreshing forecast outputs.
- Tracking refresh status.
- Streaming job/pipeline events to the frontend.

This enables the product to behave like an operational planning system rather than a one-time static report.

#### 11. Export and Handoff

The system includes export capabilities so results can be shared outside the application.

Users can export or use generated outputs such as:

- Forecast recommendations.
- SKU-level summaries.
- Monthly forecast details.
- CSV/Excel outputs generated by the pipeline.

This is useful for buyers, finance, management, or ERP upload workflows where decisions made in the dashboard need to be communicated or executed elsewhere.

### Complete User Flow

The following user flow describes how a business user would typically use the software from the start of a season through final decision-making.

#### Step 1: Start With Season Setup

The user begins in the Setup area. Here, they configure the business context for the season.

The user provides or confirms:

- Season name or active season context.
- Overall buying budget.
- Target margin percentage.
- ERP sync or raw CSV data source.

This step gives the system the commercial constraints it needs. The forecast is not reviewed in isolation; it is tied to budget and margin targets from the start.

#### Step 2: Sync or Ingest ERP Data

After the season context is prepared, the user triggers data ingestion.

The software reads ERP order data containing:

- Customer information.
- Product references.
- Colors and sizes.
- Order dates.
- Order quantities.
- Delivered quantities.
- Stock and supplier pipeline quantities.
- Product metadata such as supplier, family, theme, model, designation, and season.

The backend normalizes the data, cleans key fields, deduplicates records, and prepares the input for forecasting.

#### Step 3: Run Forecast Refresh

The user then starts a forecast refresh.

The backend pipeline runs the forecasting modules in sequence:

1. Data preparation and cleaning.
2. Model assignment.
3. KPI computation.
4. SARIMA forecasting for long-history products.
5. CatBoost forecasting for shorter-history products.
6. Size curve distribution.
7. Recommendation and net-to-order calculation.
8. Output export and database population.

Once complete, the SQLite database is populated with the latest forecast, stock, recommendation, customer, and historical demand data.

#### Step 4: Review the Dashboard

The user lands on the Dashboard to understand the overall state of the season.

They review:

- Total forecast quantity.
- Expected turnover.
- Forecasted purchase cost.
- Gross margin.
- Client coverage.
- Risk count.
- Forecast confidence distribution.

This gives a quick executive-level answer: "Is the season forecast commercially healthy, and where do we need to focus?"

#### Step 5: Inspect Product Catalog and Forecast Inputs

The user can move to the Products page to browse the product assortment.

Here, they can:

- Search for specific products.
- Filter by supplier, family, theme, model, or customer context.
- Review style/designation data.
- Confirm that product metadata coming from ERP looks correct.
- Identify important references for deeper review.

This step is useful before making purchase decisions because it confirms that the product universe and metadata are understandable.

#### Step 6: Analyze Projection at SKU, Color, and Size Level

The user then opens the Projection page for detailed stock and demand analysis.

For a selected SKU/color, the user sees a matrix across sizes. This matrix explains how forecasted demand compares with stock and supplier pipeline.

The user can answer:

- Which sizes are forecasted to sell?
- Which sizes already have enough current stock?
- Which sizes are covered by supplier orders?
- Which sizes still need purchasing?
- Is the total supplier order aligned with forecasted demand?

This is where the buyer can move from product-level strategy to actual size-level buying decisions.

#### Step 7: Review Buying Recommendations

Next, the user reviews the Recommendations page.

The system surfaces products that require action, such as:

- Buy more.
- Review low-confidence forecast.
- Watch potential overstock.
- Prioritize high-demand products.
- Check supplier/pipeline coverage.

The user can inspect each recommendation, understand the forecast basis, and decide whether to accept it, adjust it, or lock it.

Locking a recommendation is useful when the buyer has made a decision based on business knowledge and wants to preserve it through later refreshes.

#### Step 8: Check Budget and Margin Impact

After reviewing recommendations, the user checks the Budget page.

This answers:

- Are recommended purchases within the season budget?
- Is forecast spend too high or too low?
- Are expected revenue and margin aligned with the target?
- Does the current buying plan need adjustment before approval?

This is where operational buying decisions are reconciled with financial control.

#### Step 9: Review Customer Coverage

The user then reviews the Customers page to understand demand and coverage from a customer perspective.

They can:

- See all real customers from the ERP-derived database.
- Separate visited vs not-visited customers.
- Review regions and customer typologies.
- Inspect a customer's purchase history.
- See what categories a customer tends to buy.
- Use similarity matching to compare not-visited customers with visited customers.

This supports sales follow-up and demand interpretation. If many important customers have not yet ordered, the user may treat forecast demand differently or trigger commercial follow-up.

#### Step 10: Validate Forecast Quality

Before finalizing decisions, the user checks the Validation page.

This helps the user identify:

- Forecasts with weak confidence.
- Products with unusual demand behavior.
- Items where stock, orders, or demand may require manual review.
- Areas where the model should not be blindly trusted.

This validation step is important for building trust in the software and for creating a responsible human-in-the-loop forecasting process.

#### Step 11: Export Results or Hand Off Decisions

Once the user is satisfied with recommendations, budget alignment, and validation checks, they export or hand off the results.

The exported outputs can support:

- Buyer review meetings.
- Supplier order preparation.
- Finance sign-off.
- Management reporting.
- ERP upload or operational execution.

At this point, the software has transformed raw ERP history into a decision-ready buying plan.

### End-to-End Value Proposition

The complete software provides an integrated planning workflow for wholesale demand forecasting. It combines ML forecasting, inventory awareness, customer coverage, financial planning, validation, and export in one operational dashboard.

For buyers, it provides SKU/color/size-level purchase guidance.

For sales teams, it highlights customer coverage and not-visited customer opportunities.

For finance, it connects forecast demand with budget and margin targets.

For managers, it provides executive dashboard visibility and risk indicators.

For operations, it produces exportable outputs that can support ordering, reporting, and ERP workflows.

The main value is that users no longer need to manually combine ERP exports, spreadsheets, stock files, customer lists, and separate forecasting scripts. The system turns those disconnected inputs into one repeatable decision process for seasonal wholesale planning.
